Folding raw-JS logic into `.g` ghosts (`Ghost/N/Reliable.g`, `Lossy.g`), three gotchas, each cost a cycle:

1. **Bare `else <stmt>` is MANGLED.** The stho translator infers blocks from indentation, so
   ```
   if (cond) a()
   else b()
   ```
   lowers to `} else { }` with `b()` **dropped** (silent — esbuild then fails "does not parse"). Always use the C-style form the working ghosts use: `if (cond) { a() } else { b() }` with `else` on the `}` line. (`for (;;)`, `while`, `?.`, `?.[k]`, arrow fns, multi-line object literals with method shorthands, and even `get x(){}` getters DO pass through fine — it's specifically the dangling `else`.)

2. **`ghost-compile`'s 12s "no response" is a REPLY-WINDOW timeout, not a failure — check disk.** `Lossy.g` (a factory returning `{recv(){…}, tick(){…}, get clock(){…}}` with arrow fns + `?.[seq]`) compiles fine HEADLESS (FlockCompile ✓) but the CLI reported "no response in 12s (editor not connected or half-open?)". It was just SLOW — the editor force-DISPLAYS the dock (a full live stho parse that error-recovery-grinds on the far-from-DSL JS), finished minutes later, and wrote `Lossy.go` anyway. So on a timeout, `ls`/`grep` the gen before assuming failure. (Brand-new files compile too — a sibling new ghost, `Reliable.g`, replied in time.) If the editor genuinely can't (or you have no :9091), render the gen headlessly: boot Story_cli, `Lang_compile_source_state` → `Lang_compile_collect` → `Lang_split_compiled` → `Lang_compile_render_module`, write to `src/lib/<gen>`.

3. **gen `.go` must exist BEFORE `CREDULER_GHOSTS` enrollment.** The acquire (`Lies_ghost_set`) does `await import('.../<gen>.go')` — it loads the pre-built gen, it does NOT compile from source. A path in `CREDULER_GHOSTS` with no `.go` on disk → the import rejects → `Creduler_ensure` throws → `%Creduler_pending` never clears → **the runner boot hangs**. So build the gen first (ghost-compile, or headless render), THEN enroll.

4. **A gen can get OVERWRITTEN with ANOTHER ghost's content shortly after ghost-compile — but NOT because of ghost-compile.** Compiling `Reliable.g`+`Peregrination.g` together (2026-06-25), `gen/Story/Peregrination.go` briefly held the correct output (verified by grep) then was overwritten with Peeroleum's compiled methods; recompiling Peregrination ALONE fixed it and held stable 30s. I first blamed "batched ghost-compile crossed a dock" — that's WRONG and the human flagged it: ghost-compile's compile source is built from FRESH DISK TEXT per-path (`Lang_compile_source_state`, never `dock.c.state` — `spec/GhostCompile_feedback_handover.md` §"decoupled") and each ticket is independent (own `path`+`corr`, editor compiles per-path, verify polls that path's served `.go` for the source dige). So batching can't cross. The real culprit is the LIVE EDITOR's own dock state (a dock keyed to one path holding another's text), in an actively-edited session — not the CLI. Mitigation regardless: after ghost-compile, grep the gen for its OWN top-level methods (a Story gen has `Run_A_*`/`Lake_*`, NOT `Peeroleum_deliver`); if crossed, recompile that one file and re-check. ([[ghost-compile-after-g-round]])

5. **A nested-closure `await` AUTO-ASYNCS the whole method → its return silently becomes a Promise.** (PereStaple swarm, cost two runs — [[peeroleum-swarm-refactor]].) `Lake_peer` was written sync, but its mock-port object literal had `send(f){ H.post_do(async()=>{ await this.partner?.recv(f) }) }` — the compiler's auto-async heuristic saw that `await` (deep inside a nested closure) and emitted `async Lake_peer(...)`. A caller that used the return WITHOUT await (`let pa = this.Lake_peer(...)`) got a PROMISE, not the value → downstream `pa.c.up`/`pa.sc.*` reads were `undefined` and threw — but the method's BODY still ran synchronously (no top-level await), so the side-effects (created particles) all existed; ONLY the returned handle was wrong, which makes it look like a data bug, not an async bug. FIX: `await` it and let the cascade propagate (caller becomes async too), or restructure so the return isn't used. TELL: grep the gen for `async <method>` you didn't write. (The original `transport(A,w)` had the same closure+auto-async but never returned anything used, so it never bit.)

6. **A `for (const i of …)` loop var named `i` is MANGLED into a create-verb call.** (MusuRecast, 2026-07-14.) `for (const i of slice)` lowered to `for (const w.i({of: 1}) slice)` — the translator read `i` as the C **create verb** and ` of ` as a peel key, so the loop head is garbage and LocalGen/esbuild fails "does not parse @ module line N" (the error quoted the garbage directly, so no `_dump` needed). FIX: never name a `for…of` loop var `i` (nor `o`/`oa`/`oai`/`r` — the receiver-verb tokens); use `ix`/`idx`/a name. (`for (const r of …)` compiled in a sibling method the same session, so which verbs bite varies — just avoid the bare verb letters.)

7. **An explicit block `{` MUST be explicitly closed — the translator does NOT auto-close on dedent.** (Stuffing distiller, 2026-07-21, cost ~12 compile cycles.) `Stuff_keyrows` opened `for (const kk of keys) {` and I let indentation "close" it (Python habit) — no `}`. The gen's method-wrapper `}` then closed the `for` instead, so the method-separator `},` appeared unbalanced → **"generated JS does not parse @ module line N:1 `},`" at the NEXT method's close** (misleading: the missing brace is in the PRECEDING method, and the error line is IMMOVABLE at that close no matter what you edit after it). `.g` method BODIES are indentation-delimited (no outer braces), but INNER control flow is verbatim JS — every `{` you open you must `}` close. Recount braces of the method whose close the error names, AND every method before it.

8. **A file whose LAST method body ends on `}` immediately before EOF fails to compile.** Same session: the exact byte-extract of a KNOWN-GOOD method (`Vtuff_keyrows`) failed standalone but compiled once a trailing `Stuff_tail(): return 1` was appended — the compiler needs a following column-0 dedent to close the last method. So a `.g` should end on a statement or a comment, never a bare method-final `}` at EOF.

9. **`ghost-compile` (editor path) CACHES stale parse errors; LocalGen is the fresh authoritative compile.** Same session: after fixing the braces, `npm run ghost-compile` kept reporting the OLD error line for several tries (the editor re-compiled a cached dock copy). `GFILES="<path>" node_modules/.bin/vitest run -c scripts/Story_cli.vitest.config.mjs scripts/LocalGen.spec.ts` reads DISK fresh, compiles via the real translator, and WRITES the `.go` — it confirmed clean while ghost-compile still showed red; a subsequent ghost-compile then also went green. On a PARSE error LocalGen leaves `source` empty (NO SOURCE — the dock Output isn't created), so you can't dump the bad gen; **bisect instead** — copy the method into a scratch `.g` (e.g. `Ghost/test/Story/X.g`, ghost-compile compiles any path without CREDULER_GHOSTS enrollment) and progressively reduce until it compiles.

Recording a BRAND-NEW Book green on the live runner (Stuffing, 2026-07-21): `run <Book>` on a fresh Book (no toc) is NEW mode → records; set `run.sc.total` in the do_fn (`if (run.sc.mode === 'new') run.sc.total = N`) to bound the record (default ceiling 30). But a prior partial run leaves a stub `wormhole/Story/<Book>/toc.snap` → step_count>0 → the run flips to CHECK mode (dbg tell: stamp `run.sc.mode` into `w.sc` and read it off `snap`), stuck at total:1; **rm the stub toc dir** for a clean new-mode record. HMR (any ghost-compile) auto-triggers the runner to run the changed ghost by its FILE PATH (an invalid Book) → it WEDGES at `begun`; heal with `runner_ask reload` then poll ping for `"running":null` before running. `runner_ask accept` is the over-the-wire re-record; new-mode auto-saves the toc without it.

Debug move that paid off: a throwaway `_dump.spec.ts` that renders the `.g` via the real path and prints the generated module around the esbuild-reported line — pinpointed the `} else { }` instantly. (That throwaway IS the sanctioned "expecting trouble" use of the soft layer — [[g-over-scattered-ts]].)
