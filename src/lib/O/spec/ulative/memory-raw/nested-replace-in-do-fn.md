`inbox.do()` wraps each do_fn in a replace transaction (`TheC._req_do_one`). So ANY `.replace()` / `.r()` / roai-replace called from INSIDE a do_fn is a replace-inside-replace and throws "nested replace" (guarded by `OPTIMISE_FOR_DX` in `Stuff.svelte.ts`).

**Fix pattern:** move the replace OUT of the do_fn — run it AFTER `inbox.do()` returns.

Concrete case (fixed 2026-07-26): `Peeroleum_rollup_faulty` does `faulty.r(...)` and was being called inside `req_unemit` (a do_fn) → nested-replace crash. Fixed by removing the call from `req_unemit` and calling `H.Peeroleum_rollup_faulty(pier)` after each `await inbox.do()` drain in `Peeroleum_deliver` (Ghost/N/Peeroleum.g). Proven snap-neutral: PereProof's step-4 `%faulty` block is byte-identical to the committed fixture, so the rollup timing change produces zero snap diff; PereComplain green.

**Second cause, same throw (fixed 2026-07-27): the hoist wasn't enough because the hoisted call was FIRE-AND-FORGET.** `Peeroleum_rollup_faulty` was a NON-async fn whose body did an un-awaited `faulty.r(...)` (opens a replace on `faulty`, yields at `await fn()`, then the next line refills — racing its own transaction), and all THREE call sites (`Peeroleum_deliver` reliable branch, `Peeroleum_deliver` lossy branch after `inbox.do()`, and `Peeroleum_runstepped`'s per-Pier cull) called it WITHOUT `await`. `Lies_deliver_soon` drains a whole BATCH of inbound frames in a loop, so two frames from one peer fire two overlapping un-awaited rollups on the SAME `faulty` instance → nested-replace. `faulty` is replaced ONLY in this fn, so the nesting can only ever be two rollups overlapping. Fix: make `Peeroleum_rollup_faulty` (and `Peeroleum_runstepped`, which owns call site 3) `async`, `await` the internal `faulty.r()`, and `await` the fn at every call site. **Lesson: hoisting a replace out of a do_fn only works if the hoisted call is `async` + awaited to completion — an un-awaited async replace is just a slower nested replace when the caller loops.** Verification still owed on a live runner: the only runner up when this landed was wedged + holding stale gen (no editor connected to HMR the new `.go`), so re-run PereProof + PereStaple after a reload and check the `%faulty` snap blocks didn't drift (awaiting rebuilds `%faulty` deterministically before the boundary snap; racy fire-and-forget may have left it a microtask stale in old fixtures).

**Repo-wide hazard map (swept 2026-07-27).** The un-awaited-async-transaction class is a LEGACY-layer disease, not a production one. Production `Ghost/**/*.g` is clean of it (Peeroleum was the lone outlier, now fixed). `src/lib/ghost/*` (the old `.svelte` ghosts, imported only by the out-of-bounds `src/lib/mostly/Modus.svelte`) is riddled: ~100+ un-awaited `.r({…})`/`.replace(…)` calls (Radios 28, Agency 17, Gardening 13, Pirating 11, Cytoscaping 10, Trust 10) — that whole generation treats async transactions as sync mutators. Standout smells there: `Cytoscaping.svelte:179` `!de.r(…)` (negates a Promise — dead operator), `Radios.svelte:1169` `….length && w.r(…)` (control flow via `&&` firing a fire-and-forget transaction). One live-core instance: `Housing.svelte.ts:1645` `C.r({[key]:1},{})` in a menu-toggle fn (low risk — event handler, no loop). **One LIVE production sibling still open: `Ghost/N/Peeroleum.g:476`** — the ephemeral/control branch dispatches its registry handler UN-awaited (`if (on) on(w, pier, frame); H.feebly_ponder(); return`) while the twin sites `:450`/`:590` await it; `swarm_hi`'s handler is async + does an `await Swarm_voucher_ok(...)` crypto check, so its state lands outside deliver's mutex window and its reject return is discarded (benign today — the handler self-gates before `Swarm_heard_hi` — but the same shape). One-word fix (`await on(...)`), owed a live-runner verify. Root cause is the core primitive itself: `TheC`'s mutation verbs are all async and defend their per-instance `X_before` invariant by THROWING, not serialising, so a missing `await` is a latent crash — the shapelier fix is to make `replace()` queue overlapping same-C transactions instead of throw.

**The stack-trace tell:** `pattern_sc = <mainkey>:1` → `TheC.replace` ← `<your rollup fn>` ← `<your do_fn>` ← `TheC._req_do_one` ← `TheC.do`. When you see a replace low in a `.do()` stack, a do_fn is mutating via replace — hoist it out. The human's phrasing for this was "probably because of a missing await" but the real cause is the transaction nesting, not await.
